DB Query Agent: model performance

Which model should write the SQL, how reliable is it, and what does it cost? Measured November 5, 2026, through OpenRouter.

Recommendation: use DeepSeek V4.1 Flash as the default. It was the only model with a perfect score, 96 of 96, at $0.032 for all three runs. Claude Sonnet 5.5 cost about 24 times as much and scored 91. Local models stay out of scope for now.

The project

DB Query Agent helps you understand your data by asking questions in plain English. It's for anyone with a database and questions about it, including founders, startups, homelabbers and teams at work. It writes the SQL, shows it for review, and runs it only when you click Run. It's an early prototype, tested so far on SQL-Dex, a 170-table Pokémon SQLite database, with Microsoft SQL Server support planned.

How a question is answered

  1. Profile, with no AI. Setup scripts record tables, keys, row counts and sample values in a local search index.
  2. Find tables, with no AI. The question is searched against that index, tolerating typos, and foreign keys connect the matches. The model typically sees 3–4k characters of schema rather than about 50k.
  3. Generate. The model writes one SELECT, using that schema and hand-written notes about the database.
  4. Check. Code refuses anything but a single read query, compiles it, and sends it back with the error if it fails. It also enforces required filters, such as language.
  5. Run on request. The connection is read-only, with a 1,000-row cap and a 10-second limit.

Stack: Vue and Vite, Hono on Bun, SQLite for testing, and any OpenAI-compatible model API. Login, saved queries, sharing and the SQL Server adapter aren't built yet.

How to read the failures

  • A wrong result is the dangerous kind. The SQL looks plausible, so a non-SQL user won't catch it. Gemma 4 26B had the most, at 11.
  • A refusal is often the table finder's fault. Several models correctly said the stats tables weren't sent to them, on the Fire-type attack and "fastest" questions. Refusing is safer than guessing, so a lower score here doesn't always mean a worse model.
  • Empty replies are wasted money. Qwen3.6 35B returned nothing 29 times and used far more output tokens, so it's slow, inaccurate and comparatively expensive here. The cause isn't confirmed. The 2,000-token reply limit is the first thing to check.

  • Price barely matters at this volume. Every model except Sonnet costs under $1.46 per 1,000 questions. A single wrong answer acted on costs far more, so choose on accuracy first.
  • Paying more didn't buy accuracy. Sonnet was the most expensive and tied for 7th.
  • List price can mislead. The Claude models were counted at 282,972 input tokens against 169,318 for DeepSeek on the same questions. So list prices alone can't predict the bill: Haiku cost $0.051 against DeepSeek's $0.032.
  • The cheapest isn't the best value. GPT-OSS 120B and GPT-6 Luna cost about half of DeepSeek, but they refused or missed several questions that DeepSeek answered.

Local models

The current call is that local isn't there yet, even with 128 GB of VRAM available, so this tool stays on hosted models with zero retention for now. That's a judgment rather than something this test measured: every run here used hosted endpoints, and nothing has been run on a DGX Spark. GPT-OSS 120B, the largest candidate considered for local use, scored 91 of 96 when hosted, so a later test would need to measure speed and accuracy on the actual hardware.

Limits of these results

  • Scores vary between runs. Differences of a few points are mostly noise. Haiku scored 96 in an earlier round and 93 here, and Gemma went from 89 to 84. Only DeepSeek stayed perfect, across six runs.
  • The test may be too easy for the top models. It's 32 questions, written by the same author as the database notes, and some were used for tuning.
  • DeepSeek's perfect score may lean on the notes. It answered questions where the finder hadn't sent the stats tables, possibly by using table names from the notes. Its SQL hasn't been reviewed to confirm this.
  • It's only Pokémon data. A real SQL Server schema will be a different and probably harder test.

Next steps

  1. Fix the table finder, and retry empty replies, so scores no longer depend on the notes.
  2. Add about 20 harder questions, including vague wording and questions with no valid answer.
  3. Rerun the top models, then settle the default.
  4. Build login, saved queries, sharing and verified queries, then the SQL Server adapter.
